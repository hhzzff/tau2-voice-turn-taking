03 · 从事件选择到判分

1 / 指定事件子集配置语言、用户模型与 seed；prepare 仅保存配置，不生成台词。
2 / 生成 TopicTopic 为空时生成主题和私有用户背景；已有 Topic 时沿用配置。
3 / 动态对话听已播放的助手音频，经 ASR 得到上下文，再决定等待、发言或触发事件。
4 / 保存证据记录实际刺激、音频播放、观察窗口、逐 tick 轨迹和模型调用日志。
5 / 时序与语义评审先检查事件有效性，再评助手行为；不完整与证据不足单独保留。

默认观察方式是 played_audio：对已交付的助手音频前缀重新识别并替换旧假设，避免使用未来 transcript。它仍是同步 ASR，不是词级对齐；识别和模型／TTS 调用耗时会影响运行。默认 1 秒的决策检查间隔不是固定事件触发时间。{{SOURCE_已播放音频观察}} · {{SOURCE_动态用户策略}}

层次实际做法不能推出的结论
物理有效性只有刺激合成并开始播放才算触发；需重叠的事件若无实际重叠，标记 invalid_trigger / not_evaluated。请求 trigger_event 不代表有效事件；运行退出码 0 只表示所选事件均被 observed，不表示全部判为 pass。
时序评审统计刺激期间／之后的助手活动秒数、刺激结束后首次发声延迟、首次安静延迟；特定事件增加停顿期发声与主动插话延迟。首次安静可能是自然停顿；再次发声不代表回答正确。当前 bench 也未按统一延迟阈值为全部打断判成功。{{SOURCE_时序评审}}
语义评审先验证用户刺激是否符合事件，再依据实际 transcript、ASR 与时序证据输出 pass / fail / inconclusive；运行不完整另记 not_evaluated。不能只用有声／无声代替内容判断。相同模型既生成用户又做 judge，需人工与独立 judge 校准。{{SOURCE_语义评审}}
记忆专项事实须先实际说出，中间有交流，再问不复述事实值的回忆问题。听完整回答后逐事实评审，使用最新更正。私有 user_context 不等于助手听过；提问是否重叠不计分。记忆回答期间禁止用户插话，持续静默默认 1 秒后结束，默认 120 秒超时视为观察未完成。{{SOURCE_记忆评审}}
推荐同时报告三个分母。
执行覆盖率 = 有效 observed 数 / selected 数；可判定率 = (pass + fail) / selected 数；已判定通过率 = pass / (pass + fail)。同时列出 inconclusive、not_evaluated 与未触发数。上述为建议的报告口径，当前 summary 保存原始计数，不自动提供这些比率。

时序以轨迹 tick 为粒度；普通 API 默认 200 ms，实际值读取 run_config。用户输出与助手输入有一 tick 的传递延迟。音频时间、tick 时间与模型计算墙钟时间须分开解释。

04 · Topic 到底从哪里来？

当前主流程：{{MODEL}} 生成生活对话情境

DuplexScenario.topic 默认空字符串。run 遇到空 Topic 时调用 generate_topic(scenario)；非空则直接使用已有配置。默认用户模型来自 config.py，也允许显式覆盖。{{SOURCE_Topic 生成}} · {{SOURCE_主入口}}

生成请求包含：配置语言、Variation seed，以及每个已选事件的完整目录契约。要求“具体日常对话主题，能自然提供所有已选事件的机会”，返回 {topic, user_context}；禁止预写开场、事件台词、顺序、时间表或固定脚本。

所以，当前 Topic 来源是模型按项目 prompt 生成；此函数没有检索外部主题语料，也没有从原 τ-bench 任务库采样。seed 在此处作为 prompt 文本传入，并非保证复现或去重的采样器。prepare 和直接 run 的默认 seed 都是 42。相同配置不保证相同对话，换 seed 也不保证换语义主题。

Topic 与用户背景保存至 scenario.json；成功返回的话题生成、动态决策和评审调用保存至 llm_calls/。私有背景和事件契约供用户模拟器使用；被测助手通过实际用户语音逐步获知背景。

05 · 是否覆盖足够多的 Topic？

目前不能证明充分。“能够生成新 Topic”只说明生成机制开放；“事件类型齐全”只说明交互行为维度有定义。源码中尚未建立主题分类、抽样配额、语义去重、主题 × 事件统计或预先设定的充分性标准。
问题当前证据判断
交互行为是否够宽？19 类目录，四组能力；运行子集由用户指定。已定义 仍需逐类有效运行的计数。
主题是否够多、够分散？模型自由生成 everyday topic，无分类与配额。未知。不同表述可能仍属于备餐／出游等同一主题。
主题与事件是否相互独立？生成 prompt 要求同时适配所有所选事件。可能偏向容易承载事件的计划类情境；这是机制风险，尚未测量其程度。
语义任务是否够广？无工具的日常对话；现有示例多为规划、偏好和约束。无法据此宣称覆盖专业知识、工具任务或高风险场景。
语言、说话人与声学条件是否充分？配置支持中／英；默认固定主用户／背景 TTS 声线，关闭无关随机音效。支持选项不等于两种语言都已测。噪声事件有三种离散刺激；多人混音和口音分层尚不能据此确认。

06 · 怎样把“Topic 够不够”变成可回答的问题

先用已有产物做主题归类，再针对空白补样本。建议给最终运行清单增加 topic_family、子场景、语言、事实／约束结构、事件子集和有效刺激标记。分类可人工复核，不靠 Topic 字符串数量判断多样性。

建议的生活主题层可变任务与约束示例
饮食与家庭生活备餐、采购、家务分工；预算、过敏／偏好、设备与时间约束。
旅行与本地活动行程、交通、活动选择；体力、天气、人数、可达性和计划变更。
工作与协作会议、沟通、任务取舍；多方偏好、截止时间、优先级冲突。
学习与知识解释解释概念、学习计划、方法比较；理解误区、追问与澄清。
数码与日常排障设置、故障诊断、方案选择；逐步补充线索、否定假设、回忆已尝试步骤。
社交与情绪交流邀请、协调、倾诉与回应；指代、隐含意图、情绪语气和旁话辨别。

以上是建议的抽样分类，不是已存在的数据集；可按产品目标调整。增加主题时保持用户动态反应，不预写事件台词或把评审标准注入被测助手。

  1. 做主题 × 事件矩阵。每格同时列 selected、有效 observed、pass、fail、inconclusive、not_evaluated。遇到事件不适合主题时标注不适用并解释，不强行制造刺激。
  2. 先做覆盖试点。例如 6 个主题层 × 每层 3 个不同子场景 × 中英 2 种语言 = 36 场／被测模型。按事件计数反向配额，避免每场都堆所有事件。36 只是试点预算示例，不是统计充分性的证明。
  3. 控制比较条件。先冻结 topic／用户背景与事件集合，再让各模型动态交互；多 seed 重复。既报按主题宏平均，也报事件计数汇总，防止高频主题主导结果。
  4. 用不确定性决定是否足够。按会话聚类估计区间，检查各主题和关键事件的有效样本量、误差范围及结论稳定性；预先约定可接受误差。新主题上结果不稳定时继续补样本。
  5. 独立检查刺激和评审。抽听用户 TTS 是否完整、事件是否自然有效，并用人工／独立 judge 复核。保留生成来源与 prompt 版本，避免生成器与评审器共同偏好掩盖失败。
