# Frozen-time open-model demo

The controller runs the existing `FullDuplexOrchestrator.initialize()/step()` and
`VoiceStreamingUserSimulator` generation, synthesis, state and chunking. A scenario
subclass selects deterministic turn-taking actions. The model runs in a separate
persistent GPU worker, launched through Merlin; the two processes exchange a shared
filesystem mailbox. The controller uses its existing local Codex login. Credentials
must not be copied into the worker bundle.

## Launch

Start the model worker in the authorized Merlin job with a shared mailbox, then on
the authenticated controller:

```bash
python -m tau2.scripts.open_model_demo \
  --model minicpm --tick-ms 1000 --scenario user_backchannel \
  --runtime-config /path/to/frozen-minicpm-runtime.json \
  --mailbox /shared/run/mailbox --output /shared/run/demo --seconds 30
```

Use `salmonn --tick-ms 80` for before-SFT checkpoint-44000. Omitting `--tick-ms`
selects the native duration. A mismatching value fails before runtime connection.
Each independent run requires a fresh empty output directory and clean mailbox.
The controller disconnects the adapter after the run, including failure.

The runtime configuration is the worker manifest containing `python`, checkpoint,
model source and settings. Supply the frozen manifest included in the validated
Merlin bundle. MiniCPM accepts only the approved base checkpoint at
`/mnt/bn/audio-visual-llm-data6/base_models/MiniCPM-o-4_5` (or a symlink to it),
and rejects `pt_path` overlays before loading weights. The resolved manifest and worker provenance are retained in
`summary.json`. See `open-model-adapter-contract.md` for the worker boundary.

Required local controller configuration:

- Existing `codex` login with access to exact model `gpt-5.6-luna`.
- `VOLCENGINE_TTS_API_KEY` with TTS resource `seed-tts-2.0` access.
- `VOLCENGINE_ASR_API_KEY` with `volc.bigasr.auc_turbo` access.

No credentials go in command arguments, committed files or provenance. The explicit
`codex/gpt-5.6-luna` route invokes an ephemeral, isolated, read-only CLI subprocess,
disables external tool capabilities, and requires utterance JSON. Other LLM routes
continue through the existing provider abstraction. A missing key, generation
error, invalid TTS audio, or ASR error fails the run. Partial completed ticks are
exported with `status: failed`.

## Scenarios

| Name | Reproducible scheduling condition | Intended behavior |
| --- | --- | --- |
| `qa` | Initial generated question, then follow-up after an ASR-heard answer and a one-second silent interval | Ordinary question/answer |
| `correction` | After opening utterance finishes and at least one second of consecutive delivered model speech | User corrects three days to one day |
| `user_backchannel` | Same delivered-speech condition | Brief user acknowledgement without taking the floor |
| `model_backchannel` | Initial generated long user utterance continues even if model speaks | Opportunity for model acknowledgement |

The scenario policy finishes each queued user utterance and otherwise waits for its
condition. It replaces the normal stochastic user turn-choice policy only for this
demo. User text is generated by Luna, and acknowledgements use the existing seeded
user backchannel phrase selection and real TTS. Model audio is always actual worker
output. A prompt asking for a long utterance does not guarantee its length.

Positive timing thresholds use ceiling conversion in explicit native-demo mode;
ordinary API runs retain their current conversion. Existing user construction also
requires at least two ticks for yield thresholds, so those are bounded at two.
The scenario policy's response opportunities use a one-second ceiling and do not
use the normal probabilistic interruption decision. At 1000 ms, physical response
latency cannot be inferred from subsecond settings.

ASR consumes only audio already delivered by the previous-tick exchange. Native
model text and speech-script metadata are removed before user history ingestion.
The ASR window is bounded to the last twenty seconds and refreshes at most once per
one simulated second during speech, plus a final speech-to-silence refresh.
Annotations record their heard interval; revisions are not word alignments. ASR
failure does not silently substitute model text. Doubao status `20000003` means no
speech was detected and is a normal empty result, recorded as a `no_speech` ASR
event with the provider status. Empty/whitespace transcripts never enter spoken
history or qualify as a heard answer for QA. Subsequent recognized speech resumes
normal transcript handling; authentication, transport and other API errors still
fail the run. Status meanings follow the provider's
[error-code reference](https://docs.volcengine.com/docs/DoubaoVoice/error-code-query?lang=zh).

## Evidence

- `conversation.wav`: aligned 8 kHz PCM16 stereo, user left and model right.
- `ticks.jsonl`: includes the initial interval, per-tick audio hashes and prior-input
  hashes, actual compute time, audio-time interval, user intended text, separately
  named model text metadata, and energy-based activity/overlap.
- `summary.json`: runtime identity, scenario intent, scheduled trigger events,
  actual overlap, ASR refresh boundaries, timing and completion status.
- `index.html`: local playback and clickable per-tick timeline.

Activity is a declared 20 ms RMS detector, threshold 128 PCM16 units. It describes
sound activity, not semantic speech. `trigger_requested` records action scheduling. `scenario_triggered` requires observed
audio: overlap during correction/user acknowledgement, continuing user speech for
a model acknowledgement opportunity, or a heard model answer before QA follow-up.
Per-event activity and overlap remain separate from semantic success. Observation
follows the generated utterance through its final playback chunk, including leading
silence and internal pauses; a later utterance cannot satisfy an earlier trigger. Semantic outcome
remains `not_assessed` until listening review. Missing triggers and model behavior
are valid reported outcomes, never filled with fabricated responses. Controller
startup time is separate from the preserved initial trajectory timing field.

Offline tests replace only external model/provider boundaries and validate the
real simulator through the existing orchestration seam. They do not establish
live provider entitlement or real-model conversation behavior. The eight real runs
remain the integration acceptance gate in ticket #6.
