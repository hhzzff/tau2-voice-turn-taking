# 动态目标变更与关联任务联动：论文、场景和评估建议

调研日期：2026-11-11。本文结合当前工作区源码和论文原始页面，回答“用户中途变更行程目的地、系统联动调整关联任务，应参考哪些研究、如何定义评估规则”。下文的新增场景、目标版本和过程指标是设计建议，尚未接入现有评分器；不代表已经运行或获得实验结果。

## 1. 优先阅读的论文

### 直接研究目标变更与动态重规划

| 论文及原始来源 | 与本需求的关系 | 可以借鉴什么 | 适用边界 |
| --- | --- | --- | --- |
| [AgentChangeBench: A Multi-Dimensional Evaluation Framework for Goal-Shift Robustness in Conversational AI](https://arxiv.org/abs/2510.18170)，2025 | 直接研究工具型对话 agent 对会话中途目标变更的适应 | 同时报告任务成功率 TSR、工具使用效率 TUE、工具调用冗余率 TCRR、目标变更恢复时间 GSRT | 属于工具工作流评估；不能直接视为实时语音打断基准 |
| [When Users Change Their Minds: Measuring and Repairing Intent Drift in LLM Agents](https://arxiv.org/abs/2609.32520)，2026 | 提出 IntentFlux，研究已撤销、已替换的旧要求仍影响最终答案或工具动作的 intent drift | 构造“最终有效目标相同”的直接指令与多轮变更对照，保留原任务可执行 grader；检查显式维护有效需求的作用 | 原文聚焦执行前意图变化；不能据此宣称已覆盖执行中的交易撤销或分布式补偿 |
| [You Changed Your Mind, The Model Didn't: Demystifying Intent in Multi-Turn Dialogue](https://arxiv.org/abs/2610.06496)，2026 | 提出 Intent-Eval，区分“提过但拒绝的方案”和“已被替换的要求” | 加入反事实对照：用户只是讨论杭州但最终仍选上海，系统就不应误改目的地 | 重点是有效意图识别；不是机票、酒店等多服务真实联动系统的完整验证 |
| [CostBench: Evaluating Multi-Turn Cost-Optimal Planning and Adaptation in Dynamic Environments for LLM Tool-Use Agents](https://arxiv.org/abs/2511.02734)，2025 | 旅行场景中的成本优化、工具失败和成本变化引发的重规划 | 在目标变更以外增加环境扰动，分别检查任务结果、执行成本与恢复能力 | 环境变化与用户改主意是不同变量；工具调用成本也不等于用户旅行预算 |

这四篇最贴近“中途改目的地”的研究问题。其中 IntentFlux 和 Intent-Eval 有助于明确什么仍然有效，AgentChangeBench 评估变更后的恢复，CostBench 补充执行环境变化与成本权衡。

引用 AgentChangeBench 时需特别说明原文口径（[全文 §4.3、§5](https://arxiv.org/html/2510.18170v1)）：GSRT 按 **turns** 记录到首次确认/相关回复、相关工具调用和目标完成的间隔，不是语音毫秒延迟。它的 recovered shift 仅要求确认新目标且没有转人工，不要求新目标已经通过工具完成；其 TSR 也是 communication、action、NL assertion 的加权分。航空政策要求转人工的本地案例不能照搬“转人工即未恢复”，更不能将 recovery rate 当作严格业务完成率。该文标注的是 NeurIPS 2025 多轮交互 **Workshop**，不是主会。

### 支撑业务状态、依赖关系和语音交互的论文

| 论文及原始来源 | 与工作区的关系 | 可借鉴的评估思路 | 适用边界 |
| --- | --- | --- | --- |
| [τ-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains](https://arxiv.org/abs/2406.12045)，2024 | 工作区业务任务和用户模拟评估的基础 | 用户、agent、工具交互；业务规则；数据库终态；用重复试验考察可靠性 | 不能把每个任务都当作动态目标变更测试，也不能用终态匹配替代全部过程合规检查 |
| [τ²-Bench: Evaluating Conversational Agents in a Dual-Control Environment](https://arxiv.org/abs/2506.07982)，2025 | 本仓库的直接研究基础，强调用户与 agent 共同影响环境 | 检查双方协作和共享环境状态，尤其适合需要用户参与操作的关联任务 | dual-control 指双方控制环境，不能等同于语音 full-duplex，也不自动表示跨机票、酒店、日历业务联动 |
| [ToolSandbox: A Stateful, Conversational, Interactive Evaluation Benchmark for LLM Tool Use Capabilities](https://arxiv.org/abs/2408.04682)，2024 | 最适合补足“任务之间有依赖、过程不能只看最后结果”的方法 | 有状态工具环境、带依赖的 milestone 检查、minefield 禁止状态；允许满足依赖的不同执行路径 | 这些机制可用于设计动态场景，但不能把它的全部任务描述成用户中途改目的地 |
| [TaskBench: Benchmarking Large Language Models for Task Automation](https://arxiv.org/abs/2311.18760)，2023 预印本 / 2024 会议论文 | 为“关联任务”提供图结构表达 | 用工具图和任务分解表达依赖，检查工具选择、参数和依赖关系 | 偏任务自动化，不能独立证明多轮用户变更后的恢复能力 |
| [TravelPlanner: A Benchmark for Real-World Planning with Language Agents](https://arxiv.org/abs/2402.01622)，2024 | 提供旅行计划的多约束评估参照 | 检查交通、住宿、日期、预算等约束及整份计划可行性 | 核心是给定旅行需求下的规划；计划可行不等于完成真实预订，也不等于已测试动态用户目标 |
| [Full-Duplex-Bench: A Benchmark to Evaluate Full-duplex Spoken Dialogue Models on Turn-taking Capabilities](https://arxiv.org/abs/2503.04721)，2025 | 对接工作区的打断、停顿、附和与话轮交接工作 | 分析接管话轮、停止/响应延迟以及交互回应质量 | 语音上及时让渡和业务上正确重规划需要分别验证；两者不能相互替代 |

建议阅读顺序：AgentChangeBench → IntentFlux / Intent-Eval → ToolSandbox → τ-bench / τ²-Bench。若重点是语音交互，再加入 Full-Duplex-Bench；若重点是旅行依赖和预算，再加入 TravelPlanner、TaskBench、CostBench。

两篇适合补充场景和状态追踪背景的经典论文：

- [MultiWOZ — A Large-Scale Multi-Domain Wizard-of-Oz Dataset for Task-Oriented Dialogue Modelling](https://arxiv.org/abs/1810.00278)，2018。多领域任务对话、belief state 和领域间信息共享；[全文 §3.1](https://arxiv.org/html/1810.00278) 明确包括初始条件查无结果后改变约束的 goal changes，不能笼统称为完全静态。但这不等于执行后跨服务事务补偿。
- [Towards Scalable Multi-domain Conversational Agents: The Schema-Guided Dialogue Dataset](https://arxiv.org/abs/1909.05855)，2019 预印本 / AAAI 2020。服务 schema、intent、slot 与跨服务状态跟踪；其 active intent / joint goal 等指标可作为理解层诊断。dynamic schema 指服务接口变化，不能等同于用户执行中变更目标。

方法细节可重点看 [IntentFlux §3–4](https://arxiv.org/html/2609.32520v1) 的 Add / Delete / Replace 与单轮配对对照、[Intent-Eval §2](https://arxiv.org/html/2610.06496v1) 的保留原意图/采纳新意图条件、[ToolSandbox §2.3](https://arxiv.org/html/2408.04682) 的 milestone DAG 和 minefields。ToolSandbox 在符合依赖的映射中寻找最佳匹配；这与强制每个工具调用按唯一脚本出现不同。[Full-Duplex-Bench §III](https://arxiv.org/html/2503.04721v3) 的打断质量和回复延迟是在 takeover 发生的条件下统计；对比时必须同时看 takeover 比例，不能忽略未响应样本。

## 2. 工作区已有能力与可复用案例

### 2.1 当前双工实验验证的是对话行为

当前入口 [duplex_bench.py](../src/experiments/tau_voice/duplex_bench.py) 使用 `mock` 环境。实验说明 [DUPLEX_BENCH.md](../src/experiments/tau_voice/DUPLEX_BENCH.md) 定义了动态事件、已播放音频证据与逐事件评审；不能将这条实验链路的通过理解为完成真实航空订单修改。

- [duplex_events.py](../src/tau2/user/duplex_events.py) 中的 `interruption.correction` 可以承载目的地纠正，`interruption.denial` 可以承载方案否定，`proactive.clarification` 可以承载含糊变更后的澄清。
- `turn_taking.handoff` 在当前工作区特指跨轮记忆：前情建立后，经过间隔交流，再检查回答是否遵守早先约束和最新更正；不是转人工。
- [duplex_evaluation.py](../src/tau2/user/duplex_evaluation.py) 已区分有效刺激、证据不足与模型失败，并要求记忆评审引用前情和实际回答。模拟器的私有背景不能证明用户已把事实说给模型听。
- [interaction-metrics.md](interaction-metrics.md) 已覆盖 yield、响应延迟及对附和/非指向语音的处理，但这些时序信号不能证明重规划正确。
- 现有 [Doubao 实验适配器](../src/tau2/voice/audio_native/doubao/discrete_time_adapter.py) 显式拒绝带工具的连接。后续接业务任务时，应分别说明哪些模型路径实际支持工具执行。

### 2.2 航空域已有很接近需求的种子任务

来源均为 [airline/tasks.json](../data/tau2/domains/airline/tasks.json)。

| 任务 ID | 已有情节 | 适合验证什么 | 当前评分不足以单独证明什么 |
| --- | --- | --- | --- |
| `13` | 用户想把 ATL→LAX 改成 ATL→LAS，坚持只改原单、不买新票；若不允许则要求转人工 | 识别目的地变更受到政策限制，并进入正确处理路径 | 默认 `DB + COMMUNICATE`，且沟通项为空；不写库并不证明真的转了人工 |
| `32` | 用户要求先从 basic economy 升到 economy，确认该步骤后再单独改为直飞 | 分步确认、阶段依赖和过程顺序 | 数据库最终正确不能独立证明两步按要求分别发生 |
| `33` | 改期成功后，用户临时追加商务舱和两件行李；超预算后尝试只升级一段，再退回经济舱并保留行李需求 | 中途追加子目标、预算约束、拒绝后退让、保留未撤销需求 | 最终订单正确不能独立证明每次新增要求都被正确理解、及时处理和确认 |

特别注意 [airline/policy.md](../data/tau2/domains/airline/policy.md)：已有订单不能直接修改 origin、destination、trip type；写入预订数据库前必须列出操作详情并取得用户明确确认。工具 API 不会代替 agent 检查所有规则。

因此，“改目的地后成功”至少有三种不同含义：

1. **规划阶段**：更新建议、查询和行程草案，尚未下单。
2. **已有订单**：按政策解释限制；只有取消条件满足、用户同意且新预订获得授权时，才能考虑取消与重新预订。不能默认替用户取消原单。
3. **用户坚持禁止的操作**：正确拒绝并在适用时转人工。不能把“成功直接改了原订单目的地”设为正确答案。

### 2.3 默认终态评分与过程评分需要区分

[evaluation.md](evaluation.md)、[任务模型](../src/tau2/data_model/tasks.py) 和 [EnvironmentEvaluator](../src/tau2/evaluator/evaluator_env.py) 表明：`actions` 通常是用于生成目标数据库状态的一条参考解，默认不是 agent 必须逐项复现的动作脚本。`reward_basis` 决定哪些组件真正参与最终奖励；仅填写 `nl_assertions` 或 `env_assertions` 不代表它们已经成为通过条件。

另一个重要边界是 [ActionEvaluator._check_actions](../src/tau2/evaluator/evaluator_action.py)：它逐项寻找匹配的工具调用，未验证调用的时间顺序、确认先后、重复执行或额外不当调用。因此，启用 `ACTION` 也不足以单独验证“先确认机票变更，再调整已获授权的接机”。

新增动态场景应单独报告过程与意图适应结果，保留原始 τ 任务分数，避免把新规则下的成绩直接当成既有排行榜分数。

## 3. 建议的典型复杂交互场景

下面是建议的测试契约。酒店、接机、日历、工具异常和补偿机制需要新增环境或专门 fixture；不能声称现有 airline 域已经支持这些业务。

| 场景 | 用户/环境变化示例 | 必须通过的规则 | 典型失败 |
| --- | --- | --- | --- |
| S1 规划中途改目的地 | 原计划去上海，介绍方案时用户改成杭州，日期和预算不变 | 后续查询和最终计划使用杭州；保留未更改的日期、人数、预算等约束；用实际回应证明已采用变更 | 口头说“好的”，继续输出上海住宿；或把原预算一起丢掉 |
| S2 出票后要求改目的地 | 用户要求修改已有航空订单目的地 | 遵守现有航空政策；解释限制；取消重订必须分别满足政策和授权；任务 `13` 中按用户要求处理转人工 | 为迎合用户直接调用工具改原单目的地；未确认就取消原票 |
| S3 关联任务联动 | 目的地/到达时间变化，影响酒店、接机和日历 | 识别受影响的依赖节点；重算城市、日期、时区和费用；区分草案更新与需要授权的真实写入；不改无关任务 | 航班去了杭州，接机仍在上海；到达日变化但酒店日期未改 |
| S4 新增约束与局部撤回 | 改期后追加升舱、行李，超预算后只撤回升舱 | 只撤回被否定的要求，保留行李及其他有效约束；保留政策禁止的边界；参考任务 `33` | 把“不要升舱”理解为取消整个行程或同时取消行李 |
| S5 提议被拒绝 / 多次反转 | “杭州怎么样？算了还是上海”；或上海→杭州→南京 | 被拒绝的提议不进入有效目标；多次明确变更采用最新有效值；不能按关键词出现就执行 | 把所有提过的城市都订一遍；最后回到最初城市 |
| S6 旧工具结果晚到 | 上海查询已发出，用户改杭州后旧查询才返回 | 为结果关联查询时的目标；旧结果不能用于新目的地的预订；必要时重新查询；区分历史记录和当前计划 | 用上海的航班 ID 提交杭州行程 |
| S7 已执行一部分后失败 | 航班已订，酒店无房或接机修改失败 | 查询实际状态；按预定义策略和授权重试、提出替代或补偿；如实列出成功、失败和待确认事项 | 宣称全部完成；擅自取消已订航班；遗留重复订单 |
| S8 重复请求与网络重试 | 用户又说一遍“改到杭州”，或工具响应超时 | 区分用户重述、重复提交与新变更；检查实际落库/支付状态；无重复预订或扣费 | 同一句重复两次就生成两张新订单 |
| S9 旁话、附和与临时支线 | 背景人说“去杭州吧”，用户只是“嗯嗯”；或先问天气再回到订票 | 只使用具有相应授权的有效指令改变目标；不把背景话或普通附和当作对未说明交易的确认；支线结束后遵循用户意图继续 | 第三者改变了主用户目的地；把“嗯嗯”当作新交易的明确批准 |
| S10 变更不明确 / 条件不满足 | “改去那个更近的城市”；或“如果涨价就别改” | 缺少关键值时针对性澄清；条件满足前不执行条件性变更；无可行解时提出有依据的替代或停止 | 猜测城市、虚构可订方案、忽略价格条件 |

S1 可先在当前无工具讨论实验中验证语义和记忆；S2/S4 可复用航空域种子；S3/S6/S7/S8 需要业务工具环境和执行轨迹才能验证真实状态。

## 4. 明确评估规则：建议新增的验收契约

### 4.1 先定义有效意图，而不是机械采用最后一句话

建议由场景作者保存对评审可见、对被测模型不可见的目标状态记录：

- `goal_version`：每次明确生效的需求变更生成新版本。
- `active_constraints`：当前有效的目的地、日期、预算、人数、偏好等；未被撤销的约束继续有效。
- `change_status`：区分提议、条件性要求、接受、更正、拒绝、撤销；讨论过不等于生效。
- `authorization_scope`：谁允许哪些操作、费用上限是多少；同意查询不等于同意付款，旧方案的确认不自动授权新方案。
- `effective_time`：变更的关键语义实际传到模型的时间；以实际输入/音频证据定位，不用模拟器生成文本的时间替代。

这些字段是建议的评审数据结构，不是当前 `Task` 或 `DuplexScenario` 已有接口。多种有效方案应定义允许的终态集合或业务不变量，不强制匹配唯一推荐文案或唯一工具序列。

### 4.2 分别验证局部事件、全过程和最终状态

1. **刺激有效性**：更正是否真的说出并传入模型；若声称是打断，是否有真实重叠；若测记忆，前情是否实际建立且存在间隔交流。没有有效刺激不能记为模型通过或失败。
2. **局部响应**：是否理解这次变更、回答相关、适当让渡；但局部说“好的”不证明最终正确。
3. **持续遵循**：后续建议与工具参数是否持续使用当前有效目标，是否保留未变约束，是否污染为旧目标或被拒绝提议。
4. **依赖一致性**：按业务依赖图检查受影响节点；城市、抵离日期、时区、关联 ID、预算等应一致。允许不同拓扑顺序；只强制必要的前置条件和用户明确要求的分步流程。
5. **政策与授权过程**：核对每次写操作的政策条件、用户确认、费用范围及执行时间；不能只凭结束时的数据库正确就判整个流程合规。
6. **结果真实性**：最终陈述与真实工具结果、订单和扣费一致；“已完成”“已退款”“已转人工”须有对应证据。

工具延迟场景应记录调用发起、结果返回和副作用提交时刻。变更生效前已经不可撤回的调用，不因后来的新指令被追溯判错；应评估 agent 随后是否核实结果、如实告知并寻求获授权的后续处理。变更后继续新发起过时目标的交易，与明确获准的补偿操作需要区分。

### 4.3 成功定义与失败归因

建议对新增场景使用以下严格成功定义，同时保留各维度明细：

`StrictSuccess = 最新有效目标的允许终态满足 ∧ 关联状态一致 ∧ 过程政策与授权合规 ∧ 最终告知真实`

“允许终态”由案例预先规定。对于政策禁止且用户坚持的请求，可以是保留原订单并正确解释、转人工；对于故意注入无房的恢复案例，可以是用户接受的替代方案或明确授权的停止状态。不能事后把任何拒绝、搁置或未完成都解释为成功。

- `pass`：有效刺激下，所声明层级的必要条件全部得到证据支持。
- `fail`：刺激有效、观察足够，而模型明确违背有效约束、执行不当操作、遗漏必须完成的响应或虚报结果。
- `inconclusive`：音频/状态证据缺失、刺激本身含糊或不成立、基础设施故障使观察无法完成。
- `not_evaluated`：事件未触发或未进入可评估流程。

有效完整观察窗口内模型始终不响应，可以是失败；不能把模型失败都归入证据不足。反过来，运行提前断连或没有真实播放的更正也不能作为失败样本。复核时保存原始判断、证据和改判理由。

### 4.4 除成功率外建议报告的指标

| 指标 | 建议定义 | 注意事项 |
| --- | --- | --- |
| 严格成功率 | 严格通过的任务数 / 可判定有效任务数 | 同时给出有效样本数、覆盖率和证据不足比例，防止靠排除样本抬高成绩 |
| 旧目标泄漏率 | 变更后仍受已失效要求影响的可判定任务比例 | 区分建议文本、只读查询和实际交易等严重度；不能把说明历史城市算作泄漏 |
| 关联约束满足率 | 已满足的必要依赖断言数 / 全部应验证的必要依赖断言数 | 分母由场景契约给定，不能由 agent 自己删掉未完成任务来缩小 |
| 变更恢复步数 / 时长 | 从有效变更输入到首次出现可验证正确新计划或动作的步数/时间 | 明确终点和时间基准；完整任务恢复另报；无恢复记失败/未恢复，不能作为零延迟 |
| 冗余工具调用 | 无新增信息或必要副作用的重复调用数量及比例 | 合理刷新库存、核实超时结果不应机械算冗余；区别于用户预算和工具成本 |
| 未授权副作用 / 重复交易 | 轨迹中发生的未授权写入、重复扣费或重复订单数 | 应作为严格成功的阻断项；可读终态不一定保留全部瞬时违规证据 |
| 语音交互时序 | yield、停止延迟、响应延迟的分布 | 只说明交互时序；保留无响应比例和 tick 分辨率，不能替代语义、政策和状态评分 |

这里的指标名称和具体定义是针对本工作区的建议；AgentChangeBench 原文的 TSR/TUE/TCRR/GSRT 应按原文口径另行复现，不能仅因名称相近就直接比较数值。当前模拟器的同步 LLM/TTS/ASR 等待和远端服务时间不完全等价，详见 [DUPLEX_BENCH.md](../src/experiments/tau_voice/DUPLEX_BENCH.md)，不能直接用模拟 tick 声称真实端到端业务恢复延迟。

## 5. 最小可实施评估组合

1. **保持最终目标相同的成对对照**：一次性给出最终目的地 vs 中途改成该目的地；控制可用工具、数据、政策和最终需求，量化变更本身造成的差异。参考 IntentFlux。
2. **加入拒绝提议对照**：提出新目的地后明确拒绝，最终目标保持不变。参考 Intent-Eval；避免把“见到新城市就覆盖”当作目标追踪。
3. **先验证语义，再验证交易**：当前双工链路跑 S1/S5/S9；航空域用任务 `13/32/33` 做政策与过程种子；扩展有状态工具环境后再跑跨服务联动与异常恢复。
4. **过程依赖 + 允许终态**：参考 ToolSandbox，为确认、写入、依赖一致性设 milestone / 禁止事件；保持合法执行路径的自由，不要求复制参考答案的全部读操作。
5. **多次试验并分层报告**：按规划/已下单、变更前/执行中、单次/反复变更、文本/语音、可恢复/受政策限制拆分；报告重复试验的成功率及不确定性。当前每模型单个录音只适合作案例分析。

可用于立项描述的研究问题是：**在多轮、可能重叠的交互中，agent 能否正确维护当前有效目标，按权限将变更传播到相关任务，并在工具异常下保持业务状态一致和告知真实？** 其评估需要同时覆盖意图追踪、计划修订、执行过程和语音交互，单独一种现有基准不足以替代全部维度。
