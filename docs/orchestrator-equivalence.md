# 编排器透明性验收

## 已确认的定义

同一模型在相同设备、权重、seed、系统提示和参数下，直接运行与经
τ-voice 编排器运行，实际收到相同时间线的音频后，响应内容应基本相同。
开口、停止和恢复说话的有效音频时间，逐项绝对误差不超过 **100 ms**。
不得用平均误差抵消单次超限。

比较对象是接入前后同一个模型。不同模型保留原生输入粒度：SALMONN
80 ms、MiniCPM 1000 ms；不能仅凭 tick 不同就判断是否公平。

## 对照路径

- 直接基线使用原始 SDK / 参考脚本的完整运行策略，不复用待测 worker
  作为唯一基线。记录原始脚本版本与播放时间定义。
- 编排路径从 `FullDuplexOrchestrator.step()` 和公开 adapter 接口观察。
- 固定音轨不依赖本次模型回答；与动态用户模拟器的行为质量验收分开。
- 固定插话位于音轨指定位置。原始音频、模型实际收到的 PCM、输入块索引、
  控制参数及输出均保存。只有意图相同、文字相同不足以证明输入等价。
- 原基线使用 `set_break` / 强制监听时，编排路径采用同样策略；不得仅在
  编排路径额外施加控制。模型原生停止与外部控制器停止分别记录。

## 时钟与验收

1. 输入音轨样本位置：检查是否漏包、重复、变序或提前读未来音频。
2. 模型原始输出：比较文本、音频块和状态转换；确定性输出优先逐项一致。
3. 播放音轨样本位置：比较开口、停止、恢复及尾音；误差上限 100 ms。
4. 墙钟：另记输入处理、音频生成、后处理耗时，不混入冻结的音频时间。

相同 seed 不自动证明 GPU 输出确定。直接基线重复运行，保留其自身差异，
避免把本来存在的波动误归因于编排器；也不能用此理由忽略系统性延迟。

初始占位 tick、上一时间片交换、前端缓存和播放 FIFO 必须各自检查。
不能通过事后整体平移输出音轨掩盖额外延迟。原始离线脚本把生成音频标在
输入块起点时，须明确这是媒体时间约定，不能当作实际墙钟开口证据。

## MiniCPM 专项

当前使用的 `MiniCPMO45/modeling_minicpmo_unified.py` 经
`core.processors.UnifiedProcessor` 暴露同步整块 `generate()` 返回，
没有在一次调用中向调用方 yield 子块音频。

独立脚本 `scripts/control_signal_probes/minicpm_timing.py` 直接调用原始
SDK，分别测量 `prefill`、`generate`、`finalize`，在各边界同步 CUDA：

- 音频可用耗时 = prefill + generate。
- 当前同步 worker 的整步耗时 = prefill + generate + finalize。
- 分别统计静音步与有声输出步，记录每步输出音频的实际长度。
- 判断是否跟得上 1000 ms 输入周期；这不是编排器 100 ms 等价性验收。
- 即使整步小于 1000 ms，仍需另外验证播放队列不会推迟音频。

首个冷启动步与后续步骤全部保留，不因超时删除。固定输入包含首次请求、
20 秒插话、32 秒 backchannel。两次原生运行采用相同输入和 seed，另跑
参考脚本的外部打断策略，不把它的结果描述为模型自主打断。

## 闭源范围

用户最新要求只比较开源模型。此前执行的闭源跨请求 A/B 混入网络和服务端
波动，已撤回作为公平性验收依据，不再继续闭源延迟对照。闭源继续沿用
用户已确认的信号处理范围；检查返回的开口、打断和结束
信号是否按服务语义及时执行，尤其是取消旧音频、保留自然结束尾音、隔离
不同 response。增加包间停发不能直接作为网络延迟已消除的证据。

## 当前状态

这是验收标准，不是通过证明。逐模型协议实测见
[控制信号审计](control-signals-audit.md)。MiniCPM 专项 GPU 计时与完整
编排器等价性对照分别报告；未完成的项目保持待验收。
