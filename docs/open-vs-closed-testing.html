01 / 接入架构

外层编排相同，模型执行边界不同

两条动态交互路径都使用 FullDuplexOrchestrator：用户和助手各自持有状态，每个 tick 交付一小段音频。模型 adapter 复用 DiscreteTimeAdapter 的输入输出、剩余音频缓冲和统计框架。

03 / 时间与交付

同样 180 秒录音，可能代表不同的运行过程

共同规则：双方接收对方上一 tick 的音频

U[n] = User(A[n−1], user_state)
A[n] = Agent(U[n−1], agent_state)
t[n+1] = t[n] + Δ

U[n]、A[n] 是这一 tick 的输出。实际 Python 执行先处理用户、再处理助手，但两份输入在处理前已取好；助手这一 tick 听到的仍是 U[n−1]。所以“在同一音频时间段双方都发声”不等于两个函数并行计算。

开源：模拟时钟等待计算

例如 MiniCPM 的 1 秒音频计算了 3 秒，音频时间仍只前进 1 秒。用户同步做 LLM / TTS / ASR 时，原生 worker 不会额外自行 step；完成后按顺序交付音频，不因此跳过输入。

闭源：远端服务有自己的时钟

adapter 以实时节奏发送并接收。用户生成仍是同步操作，但远端服务和后台连接可能继续推进、积累事件。默认 realtime 只是实现模式，不保证整个闭环每 200 ms 准点完成。

04 / 最容易误读的行为差异

用户说话时，模型插话能不能让用户停下来？

这取决于用户策略入口，不能仅按“开源 / 闭源”二分。共同的基础执行器已经会处理 stop_talking：取消还没播放的用户音频，并在当前间隔输出非语音；这里取消的是播放队列，完整文本与 TTS 往往已经同步生成好了。

路径队列里还有用户语音时意味着什么
标准 API 用户
VoiceStreamingUserSimulator		进入 basic_turn_taking_policy；结合重叠发起方、持续发声与阈值，可能选择 stop_talking具备按阈值让话的机制；短 backchannel 受保护。仍需考虑共享状态缺陷。
闭源动态事件 bench
DuplexUserSimulator		通常直接 keep_talking；特定 proactive.contextual_interruption 有提前清队列分支。事件观察中通常等待。用户事件话语与观察窗口受到保护；不能认为它完全继承标准 API 用户的让话行为。
开源基础 4 场景
qa / correction / user_backchannel / model_backchannel		有队列就 keep_talking，优先把这次用户话语播完方便稳定提供待测刺激，但普通用户长句也可能不会因模型插话而取消。
开源
ordered_conversation		函数最前面检查队列，非空就继续播放；这个检查也先于后续 free_dialogue 分支阶段顺序受控，后续普通回复仍受这个覆盖影响；不能把“后来进入自由对话”理解为恢复全部让话策略。
开源
long_conversation		普通播放委托给通用用户策略；另外根据已听音频与场景约束限制打断 / 附和机会更接近标准用户的动态交互；与 ordered 的行为不同。
最新 SALMONN 固定回放
run_phase.py		直接逐包送入既有用户录音；没有在线用户生成与让话决策用户不会根据本轮 SALMONN 的新回复停说、重述或改变后续话语。
具体例子：用户正在讲旅行偏好，模型开始插话。标准用户达到适用阈值后可能清空余下音频；开源基础 / ordered 场景通常继续播完。因此更长的重叠可能来自用户策略，不能直接判为“这个模型更不会打断”或“更不会让话”。闭源动态事件 bench 的队列保护也要单独检查。

1 秒阈值，在两种原生 tick 下并不等长

开源 demo 将秒数向上换算成 tick，再对让话阈值执行 max(2, ticks)。默认“用户被模型打断”的目标阈值是 1 秒：

SALMONN · ceil(1 / 0.08)13 ticks = 1.04 秒
MiniCPM · max(2, ceil(1 / 1))2 ticks = 2 秒

这是会进入基础让话策略时的名义阈值；不包含上一 tick 交付与其他策略影响，也不保证在上面强制 keep_talking 的分支生效。用户主动抢话后坚持发言的默认阈值则是 5 秒。

当前还存在的共享状态问题

单个 chunk 的 backchannel 取出后，执行器仍无条件设 is_backchanneling=True；如果队列已空，标志不会在这一分支清除。后续普通回复可能继承“附和不可打断”状态。该问题在共享执行器中，API 与原生路径都可能受影响，1 秒 tick 更容易把短附和装进一个 chunk。

另外，ordered 在话语实际播完前已推进阶段；如果未来恢复取消播放，队列变空不能直接代表纠正内容已完整送达。现有审计提出了修正方向，但本页不把这些建议写成已修复功能。

依据：基础话轮策略 · 动作执行器 · 开源场景策略 · 闭源事件用户 · 2026-11-02 用户策略审计

05 / 观察与评分

“模型确实发声”与“通过行为评测”是不同结论

开源 demo：先保留交互证据

场景用户去掉原生文本和脚本元数据，再识别已经交付的模型音频。豆包 ASR 使用最近最多 20 秒的窗口，发声中通常最多每模拟秒刷新一次，并在转入静音时补刷新；滚动识别会修订，不能当作逐词对齐。

导出器分别记录“请求了触发”与“实际观察到触发”。纠正 / 用户附和可用真实重叠证明刺激出现，但不据此判断纠正被理解或模型附和自然。语义结果默认保留为 not_assessed。

闭源事件 bench：再进入事件评审

默认 played_audio 模式用已播放助手音频的 ASR 前缀给 Terra 决策，保留音频段与识别快照；也可显式选 proportional 近似文本。默认模式是同步检查点 ASR，会增加墙钟等待。

对话结束后，assess_report 计算时序证据，再由 judge_report 对已观察事件做语义判断；失败、证据不足与未观察事件保留相应状态。跨话轮记忆另用事实级评审，不把及时发声当作记忆正确。

共同的证据边界：用户计划文本不保证 TTS 全部读出；助手解码文本不等于实际说出的音频。闭源 bench 已保存原始 TTS、脚本、时长与哈希，但标准运行仍未自动对用户侧 TTS 做完整 ASR 核验。重叠率、阶段请求数、退出码或绿色单测都不能替代语义和听音验收。

测试“种类数”也不能等同于覆盖

开源 6 个 scenario ID 都围绕北京旅行，不能算成 6 个不同主题。闭源的 19 类事件是可选测试定义；Topic 由模型生成，目前也不能仅凭生成了不同字符串，就认定有充分的主题分类、去重或 Topic × 事件覆盖。

依据：export_demo() · PlayedAudioPerception · 事件评审 · bench 证据说明 · 既有评估范围报告

06 / 当前已有证据

最新开源验证里，有动态对话，也有固定音频回放

11 月 1 日 · 旧 checkpoint 的交互记录MiniCPM 的 180 秒录音请求了全部五个用户阶段；旧 SALMONN 录音在问候和用户纠正后没有继续完成后续阶段。这是历史配置下的行为记录，不能直接套到 11 月 2 日新选 checkpoint。

11 月 2 日 · 当前 SALMONN checkpoint 与原生执行验证默认已切到指定 0519 / Llama 3.1 checkpoint-44000，并按它自己的训练配置加载。MiniCPM 的原生 SDK 对照验证了 75 步输入及返回 flags / text / PCM 一致性；这是接口对照证据。

11 月 2 日 · 最终代码 180 秒 SALMONN replay使用既有 MiniCPM 用户轨道的 179 秒，加 1 秒明确静音，重切成 2,250 个 80 ms 输入包。实际 GPU 是 NVIDIA A100-SXM4-80GB；输入和输出哈希、样本总量及因果特征检查通过。模型出现多次重新发声与 listening transition，但这次没有在线用户模拟器。

这轮验证确认了哪些内容：最终原生代码能够因果接收这些输入包并产生可审计输出。它没有确认新 checkpoint 与动态用户完成自然长对话，也没有证明理解纠正、自然附和或端到端实时性。本次说明没有新启动模型、调用付费语音服务或重跑评测。
SALMONN 自身音频反馈也已随当前配置变化

worker 的实现是“当前用户输入 + 上一实际播放的 80 ms 模型音频 × echo_ratio”，不会读排队中的未来音频。但当前选定 checkpoint 的训练配置使 echo_ratio = 0。因此不能沿用旧版本“默认 1.0，所以模型一定听见自己”的说法。另一个 30 秒参数是声学 encoder 分块，和 80 ms 调度 tick 不同。

07 / 对结果的实际影响

现在适合分别看工程接入与行为证据；横向排名还缺协议对齐

如果目标是比较“同样情况下谁更会打断、谁能理解纠正”，只统一音频时长还不够。至少需要把下面几项固定下来：

  1. 同一用户播放 / 让话规则。普通发言、附和与取消播放的处理一致；被截断阶段不能当成已经完整交付。
  2. 同一任务和可听信息。固定待测事件、约束与观察方式，记录模型实际收到哪些内容；同时控制用户 LLM、TTS、ASR、语言和声线。
  3. 区分行为时间与运行时间。保留各模型原生 tick，但说明物理阈值换算和边界误差；冻结时间结果与墙钟实时性能分开报告。
  4. 接入同一评审和分母。用实际录音与交付证据评审，分别统计有效触发、未触发、无效 / 不完整轨迹、语义成功及不确定结果。

固定回放适合隔离 worker / checkpoint 改动，动态用户适合测试“模型回应改变用户下一步”的闭环。两者各有用途，结果应注明实验类型。以上是对齐建议，尚未表示仓库已完成这些改动。
